# Índices

> Um **índice** é uma estrutura criada pelo SGBD para encontrar registros de forma mais eficiente, evitando que o banco precise percorrer toda a tabela em determinadas consultas.

- Permite acesso mais rápido aos dados.
    
- Funciona como uma espécie de **referência para encontrar registros**.
    
- Utiliza diferentes algoritmos e estruturas de dados, dependendo do tipo de índice.
    
- Pode melhorar bastante a velocidade das consultas.
    
- Em contrapartida, pode deixar operações de escrita mais lentas.
    

## 1. Como os índices funcionam

> O índice cria uma estrutura organizada que permite ao banco localizar os registros sem precisar procurar um por um dentro da tabela.

Algumas estruturas utilizadas pelos SGBDs são:

- **B-Tree / B+Tree** — muito utilizada para buscas e ordenações.
    
- **Hash** — eficiente para buscas por igualdade.
    
- **GiST** — utilizada para diferentes tipos de dados e buscas especializadas.
    
- **SP-GiST** — utilizada para estruturas que podem ser divididas em diferentes partições.
    
- **GIN** — muito utilizada para dados que possuem múltiplos valores associados, como arrays e alguns tipos de documentos.
    
- **R-Tree** — utilizada principalmente para dados espaciais em sistemas que oferecem esse suporte.
    

> Cada estrutura possui uma finalidade diferente. A escolha depende do tipo de consulta e dos dados que serão indexados.

## 2. Índices e performance

> O índice cria um equilíbrio entre **velocidade de leitura** e **custo de escrita**.

- Consultas podem ficar mais rápidas.
    
- `INSERT`, `UPDATE` e `DELETE` podem ficar mais lentos.
    
- Quando um registro é alterado, o SGBD também pode precisar atualizar os índices relacionados.
    
- Quanto mais índices uma tabela possui, maior pode ser o custo das operações de escrita.
    
- Por isso, não é recomendado criar índices sem analisar como a tabela é realmente consultada.
    

### 2.1 Trade-off dos índices

```text
Mais índices
     ↓
Consultas SELECT mais eficientes
     ↓
Porém...
     ↓
INSERT / UPDATE / DELETE podem ficar mais caros
```

> **Resumo:** índices normalmente melhoram a leitura, mas aumentam o trabalho necessário para manter os dados indexados.

# Armazenamento das tabelas

> O SGBD não armazena uma tabela como um único bloco gigante. Os dados são armazenados em **páginas**, que são unidades menores de armazenamento.

## 3. Tabelas HEAP

> Uma tabela **HEAP** é uma tabela em que os registros não possuem uma ordenação física definida por um índice clusterizado.

No PostgreSQL, por exemplo:

- Os dados das tabelas são armazenados em páginas.
    
- As páginas possuem tamanho limitado.
    
- Uma tabela pode ocupar várias páginas.
    
- Os registros não ficam necessariamente organizados pela ordem de uma coluna.
    
- O banco utiliza estruturas auxiliares, como índices, para localizar os registros mais rapidamente.
    

> **Importante:** o conceito de HEAP pode variar entre SGBDs. Portanto, não devemos assumir que toda tabela sem chave primária seja exatamente uma HEAP da mesma maneira em todos os bancos.

### 3.1 Página

> Uma **página** é uma unidade de armazenamento utilizada pelo SGBD para organizar os dados no disco.

No PostgreSQL, por exemplo, o tamanho padrão de uma página é **8 KB**.

```text
Tabela
│
├── Página
├── Página
├── Página
├── Página
└── ...
```

# Tabelas Clustered e Non-Clustered

## 4. Índice Clusterizado

> Um **índice clusterizado** determina a ordem física em que os dados de uma tabela são armazenados.

- Os registros ficam organizados de acordo com a chave do índice.
    
- Normalmente existe apenas **um** índice clusterizado por tabela, porque os dados só podem ter uma organização física principal.
    
- É útil quando as consultas frequentemente trabalham com uma determinada ordem ou intervalo.
    

> A implementação desse conceito varia bastante entre SGBDs. O PostgreSQL, por exemplo, não possui um índice clusterizado permanente da mesma forma que alguns outros bancos.

### 4.1 Índice Non-Clustered

> Um **índice não clusterizado** é uma estrutura separada dos dados da tabela que permite localizar os registros.

Ele pode ser imaginado assim:

```text
Índice
│
├── Valor → referência para registro
├── Valor → referência para registro
└── Valor → referência para registro

             ↓

Tabela
├── Registro
├── Registro
└── Registro
```

- O índice possui os valores das colunas indexadas.
    
- Mantém referências para os registros reais.
    
- A tabela continua armazenando os dados separadamente.
    
- É possível ter vários índices desse tipo em uma tabela.

# Algoritmo B-Tree

## 5. B-Tree / B+Tree

> **B-Tree** é uma estrutura de dados em árvore utilizada para organizar valores de forma que o banco consiga encontrar informações rapidamente.

É uma das estruturas mais comuns para índices.

- Mantém os valores organizados.
    
- Permite buscas eficientes.
    
- Funciona muito bem com comparações.
    
- Pode ser utilizada em consultas com `=`, `<`, `>`, `<=`, `>=` e intervalos.
    
- Também pode ajudar em consultas que precisam de dados ordenados.
    

### 5.1 Exemplo simples

Imagine uma tabela com id:

```text
1
5
8
12
20
25
30
```

Sem índice, o banco pode precisar verificar vários registros até encontrar o que procura.

Com uma B-Tree, os valores ficam organizados em uma estrutura semelhante a uma árvore:

```text
             12
           /    \
         5       25
        / \     /  \
       1   8   20   30
```

> O banco consegue percorrer a árvore e chegar ao valor procurado sem verificar todos os registros.

### 5.2 Consultas por intervalo

> Uma das vantagens da B-Tree é trabalhar bem com **intervalos de valores**.

Por exemplo:

```sql
SELECT *
FROM usuarios
WHERE idade BETWEEN 18 AND 30;
```

Como os valores estão organizados, o índice pode ajudar o banco a encontrar rapidamente a região correspondente ao intervalo.

# Índice Composto
## 6. Índice Composto / Multicolumn Index

> Um **índice composto** é um índice que utiliza duas ou mais colunas da mesma tabela.

- É útil quando determinadas consultas utilizam frequentemente várias colunas juntas.
    
- Pode melhorar consultas que filtram ou ordenam por essas colunas.
    
- A **ordem das colunas no índice é importante**, principalmente em índices B-tree.
    
- Deve ser criado com base nas consultas que realmente são executadas pela aplicação.
    
- Não devemos colocar várias colunas no índice simplesmente porque "quanto mais colunas, melhor".
    

### 6.1 Exemplo

Imagine uma tabela:

```sql
CREATE TABLE usuarios (
    id BIGINT,
    nome VARCHAR(100),
    email VARCHAR(255),
    idade INT
);
```

E uma consulta frequente:

```sql
SELECT *
FROM usuarios
WHERE nome = 'João'
  AND idade > 18;
```

Podemos criar um índice composto:

```sql
CREATE INDEX idx_usuario_nome_idade
ON usuarios (nome, idade);
```

Nesse caso, o índice utiliza:

```text
(nome, idade)
```

### 6.2 Ordem das colunas

> A ordem das colunas no índice composto influencia a forma como o banco consegue aproveitá-lo.

Por exemplo:

```sql
CREATE INDEX idx_usuario
ON usuarios (nome, idade);
```

Temos:

```text
1º nome
2º idade
```

A coluna `nome` é a **primeira coluna do índice**, também chamada de coluna mais à esquerda (_leftmost column_).

Em um B-tree, as condições sobre as colunas mais à esquerda são especialmente importantes para restringir a parte do índice que precisa ser percorrida.

### 6.3 Como escolher a ordem?

> A ordem deve ser escolhida observando **como as consultas realmente utilizam as colunas**, e não apenas escolhendo a coluna com maior quantidade de valores diferentes.

Por exemplo, se temos frequentemente:

```sql
WHERE usuario_id = ?
AND status = ?
```

podemos considerar:

```sql
CREATE INDEX idx_pedido_usuario_status
ON pedidos (usuario_id, status);
```

A ideia é colocar primeiro as colunas que fazem parte dos filtros mais importantes e frequentes da consulta.

### 6.4 Igualdade e intervalo

> Em um índice B-tree, é comum que colunas usadas com **igualdade (`=`)** sejam colocadas antes de uma coluna usada com **intervalo**, como `>`, `<`, `BETWEEN` ou similares.

Por exemplo:

```sql
SELECT *
FROM pedidos
WHERE usuario_id = 10
  AND data_pedido >= '2026-01-01';
```

Um índice como:

```sql
CREATE INDEX idx_pedido_usuario_data
ON pedidos (usuario_id, data_pedido);
```

pode ser uma boa escolha para esse padrão de consulta.

A documentação do PostgreSQL explica que, em B-tree multicoluna, condições de igualdade nas colunas iniciais, seguidas pela primeira condição de desigualdade, são utilizadas para restringir a parte do índice que será percorrida.

### 6.5 Evitar índices com muitas colunas

> Um índice composto não deve ter várias colunas sem necessidade.

Por exemplo, criar:

```sql
CREATE INDEX idx_usuario
ON usuarios (nome, email, idade, cidade, telefone, cpf);
```

não significa automaticamente que todas as consultas ficarão mais rápidas.

- O índice ficará maior.
    
- As operações de escrita podem ficar mais caras.
    
- Pode consumir mais espaço.
    
- Pode ser desnecessário para as consultas reais da aplicação.
    

É recomendo usar índices multicoluna com moderação e observa que índices com mais de três colunas tendem a ser pouco úteis, salvo casos específicos.

### 6.6 Criar o índice baseado nas consultas

> A melhor forma de decidir um índice composto é analisar as **consultas que realmente são executadas**.

Por exemplo, se a aplicação frequentemente executa:

```sql
SELECT *
FROM pedidos
WHERE cliente_id = ?
AND status = ?;
```

faz mais sentido considerar:

```sql
CREATE INDEX idx_pedidos_cliente_status
ON pedidos (cliente_id, status);
```

do que simplesmente criar índices compostos com várias colunas sem observar o uso real.

### 6.7 Índice composto × vários índices simples

> Nem sempre um índice composto é melhor que vários índices individuais. O planejador do banco pode, em alguns casos, combinar diferentes índices para executar uma consulta.

Por exemplo:

```sql
CREATE INDEX idx_cliente
ON pedidos (cliente_id);

CREATE INDEX idx_status
ON pedidos (status);
```

pode ser uma alternativa a:

```sql
CREATE INDEX idx_cliente_status
ON pedidos (cliente_id, status);
```

A escolha depende das consultas e dos dados. O PostgreSQL pode combinar índices utilizando _bitmap scans_, mas isso também possui custos e pode não ser melhor que um índice composto adequado.

### 6.8 Índice composto para `ORDER BY`

> Índices compostos também podem ajudar consultas que precisam retornar os dados em uma determinada ordem.

Por exemplo:

```sql
SELECT *
FROM pedidos
WHERE cliente_id = 10
ORDER BY data_pedido;
```

Um índice:

```sql
CREATE INDEX idx_pedidos_cliente_data
ON pedidos (cliente_id, data_pedido);
```

pode ajudar tanto no filtro por `cliente_id` quanto na ordenação por `data_pedido`.

Índices B-tree podem ser utilizados para determinadas ordenações, e a ordem definida nas colunas do índice pode ser importante para consultas com `ORDER BY`.

### 6.9 Regra prática

> Antes de criar um índice composto, pense em **como a aplicação consulta os dados**.

```text
Consulta frequente
      ↓
Quais colunas aparecem no WHERE?
      ↓
Quais aparecem no ORDER BY?
      ↓
Qual é a ordem dessas colunas?
      ↓
O índice realmente reduz o trabalho do banco?
      ↓
Criar e testar o índice
```

# Covering Indexes
## 7. Covering Indexes

> Um índice que contém todas as informações necessárias para uma determinada consulta, permitindo que o banco consiga responder à consulta usando apenas o índice, sem precisar acessar a tabela principal.

- Pode deixar determinadas consultas mais rápidas.
    
- Reduz a necessidade de acessar os dados da tabela.
    
- É especialmente útil para consultas que retornam poucas colunas.
    
- Pode aumentar o tamanho do índice.
    
- Também aumenta o custo de manutenção do índice durante `INSERT`, `UPDATE` e `DELETE`.
    

## 7.1 Como funciona

Imagine uma tabela:

```sql
CREATE TABLE usuarios (
    id BIGINT,
    nome VARCHAR(100),
    email VARCHAR(255),
    idade INT
);
```

E uma consulta:

```sql
SELECT nome, email
FROM usuarios
WHERE idade = 20;
```

Podemos criar um índice que contenha todas as informações necessárias:

```sql
CREATE INDEX idx_usuarios_idade
ON usuarios (idade)
INCLUDE (nome, email);
```

Agora o índice possui:

```text
idade → nome → email
```

Quando a consulta for executada, o banco pode encontrar os registros e obter `nome` e `email` diretamente do índice.

### 7.1.1 Índice normal

Sem um Covering Index, o fluxo pode ser:

```text
Índice
  ↓
Encontra o registro
  ↓
Vai até a tabela
  ↓
Busca nome e email
  ↓
Retorna resultado
```

### 7.1.2 Covering Index

Com um Covering Index:

```text
Índice
  ↓
Encontra o registro
  ↓
Já possui nome e email
  ↓
Retorna resultado
```

> A ideia principal é **evitar o acesso adicional à tabela** quando o índice já possui tudo que a consulta precisa.

## 7.2 `INCLUDE`

> `INCLUDE` permite adicionar colunas ao índice apenas para que elas estejam disponíveis durante a consulta, sem fazer parte da chave usada para organizar o índice.

```sql
CREATE INDEX idx_usuarios_idade
ON usuarios (idade)
INCLUDE (nome, email);
```

Nesse exemplo:

- `idade` é a coluna utilizada para localizar os registros.
    
- `nome` e `email` ficam armazenados no índice para cobrir a consulta.
    
- `nome` e `email` não são utilizados como parte da chave de busca do índice.

# Índice Parcial

## 8. Partial Index

> Um **índice parcial** é criado apenas para uma parte dos registros de uma tabela, definida por uma condição `WHERE`.

Isso pode reduzir o tamanho do índice e o custo de manutenção quando apenas uma parte dos dados é frequentemente consultada.

### 8.1 Exemplo

Imagine uma tabela com milhões de usuários, mas a aplicação consulta frequentemente apenas usuários entre 15 e 40 anos.

Podemos criar:

```sql
CREATE INDEX idx_usuarios_idade
ON usuarios (idade)
WHERE idade BETWEEN 15 AND 40;
```

Nesse caso, o índice não precisa considerar todos os registros.

```text
Tabela
│
├── idade 10  → fora do índice
├── idade 14  → fora do índice
├── idade 15  → indexado
├── idade 20  → indexado
├── idade 30  → indexado
├── idade 40  → indexado
└── idade 50  → fora do índice
```

- É criado utilizando uma condição `WHERE`.
    
- Indexa apenas os registros que atendem à condição.
    
- Pode ocupar menos espaço.
    
- Pode reduzir o custo de manutenção.
    
- É útil quando uma determinada parte dos registros é consultada com muita frequência.
    

> **Importante:** índice parcial não significa índice clusterizado. São conceitos diferentes.

# Criação de Índices de Forma Concorrente

## 9. `CREATE INDEX CONCURRENTLY`

> A criação concorrente de índices permite criar um índice sem bloquear da mesma forma o acesso normal à tabela durante todo o processo.

No PostgreSQL, podemos utilizar:

```sql
CREATE INDEX CONCURRENTLY idx_usuarios_email
ON usuarios (email);
```

### 9.1 Por que utilizar?

Imagine uma tabela que está sendo utilizada constantemente pela aplicação.

Criar um índice de forma tradicional pode causar bloqueios que atrapalham determinadas operações.

Com:

```sql
CREATE INDEX CONCURRENTLY
```

o PostgreSQL cria o índice de forma que reduz o impacto sobre as operações concorrentes da tabela.

- É útil em bancos de produção.
    
- Reduz bloqueios durante a criação.
    
- Pode demorar mais que a criação normal.
    
- Possui algumas restrições específicas.
    
- É uma funcionalidade específica do PostgreSQL, não uma regra geral de SQL.
    

### 9.2 Exemplo

Forma tradicional:

```sql
CREATE INDEX idx_email
ON usuarios (email);
```

Forma concorrente no PostgreSQL:

```sql
CREATE INDEX CONCURRENTLY idx_email
ON usuarios (email);
```
