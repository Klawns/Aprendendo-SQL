#db 
## 14.1 O que são

Triggers, ou **gatilhos**, são ações automáticas associadas a uma tabela.

Eles são executados automaticamente quando determinado evento acontece.

Por exemplo:

```text
INSERT → adicionou um registro
UPDATE → alterou um registro
DELETE → removeu um registro
```

Podemos configurar o banco para executar alguma lógica automaticamente quando esses eventos acontecerem.

### Exemplo da vida real

Imagine um sistema financeiro:

```text
Usuário cria uma transação
        ↓
INSERT na tabela transactions
        ↓
Trigger é executado
        ↓
Registra uma informação na tabela de auditoria
```

A aplicação não precisa chamar a auditoria manualmente.

---

## 14.2 Sintaxe

Estrutura básica:

```sql
CREATE TRIGGER <trigger-name>
BEFORE/AFTER INSERT/DELETE/UPDATE ON <table>
FOR EACH ROW
BEGIN
    -- bloco de código
END;
```

Exemplo:

```sql
CREATE TRIGGER after_transaction_insert
AFTER INSERT ON transactions
FOR EACH ROW
BEGIN
    INSERT INTO transaction_audit(transaction_id, action)
    VALUES (NEW.id, 'INSERT');
END;
```

Nesse exemplo:

```text
INSERT em transactions
        ↓
Trigger é executado
        ↓
INSERT em transaction_audit
```

---

## 14.3 FOR EACH ROW

O:

```sql
FOR EACH ROW
```

significa que o Trigger será executado **para cada linha afetada**.

Imagine:

```sql
UPDATE products
SET price = price * 1.10
WHERE category = 'BOOK';
```

Se 100 produtos forem alterados, o Trigger pode ser executado **100 vezes**, uma para cada linha.

Por isso, é importante tomar cuidado com a lógica colocada dentro de Triggers.

---

## 14.4 NEW e OLD

Dentro de um Trigger podemos acessar os valores da linha através de `NEW` e `OLD`.

### NEW

Representa o **novo valor** da linha.

Exemplo:

```sql
NEW.price
```

Pode ser utilizado quando uma linha está sendo inserida ou quando está sendo atualizada.

### OLD

Representa o **valor antigo** da linha.

Exemplo:

```sql
OLD.price
```

É útil principalmente para saber o que existia antes de uma alteração ou exclusão.

### Exemplo

Imagine:

```text
Preço antigo: R$ 100
Preço novo:   R$ 120
```

Em um `UPDATE`:

```sql
OLD.price → 100
NEW.price → 120
```

Isso é muito útil para auditoria.

---

## 14.5 BEFORE

`BEFORE` significa:

> Execute o Trigger **antes** da operação acontecer.

Exemplo:

```sql
CREATE TRIGGER before_product_insert
BEFORE INSERT ON products
FOR EACH ROW
BEGIN
    -- alguma validação
END;
```

Fluxo:

```text
INSERT
  ↓
BEFORE TRIGGER
  ↓
Registro é inserido
```

### Onde usar?

Pode ser usado para:

- validar dados;
    
- ajustar valores;
    
- preencher informações;
    
- impedir uma operação inválida.
    

Por exemplo, podemos verificar alguma condição antes de permitir a criação de um registro.

---

## 14.6 AFTER

`AFTER` significa:

> Execute o Trigger **depois** da operação acontecer.

Exemplo:

```sql
CREATE TRIGGER after_product_insert
AFTER INSERT ON products
FOR EACH ROW
BEGIN
    INSERT INTO product_audit(product_id, action)
    VALUES (NEW.id, 'CREATED');
END;
```

Fluxo:

```text
INSERT
  ↓
Registro criado
  ↓
AFTER TRIGGER
  ↓
Registra auditoria
```

### Onde usar?

É bastante útil para:

- auditoria;
    
- histórico;
    
- registrar alterações;
    
- atualizar informações relacionadas.
    

---

## 14.7 INSERT

Executado quando uma nova linha é inserida.

```sql
AFTER INSERT
```

Exemplo real:

```text
Novo pedido criado
        ↓
Trigger
        ↓
Registra histórico do pedido
```

Nesse caso, podemos utilizar:

```sql
NEW.id
NEW.customer_id
NEW.total
```

---

## 14.8 UPDATE

Executado quando uma linha é alterada.

Podemos comparar:

```sql
OLD
```

com:

```sql
NEW
```

Exemplo:

```text
Antes:
status = PENDING

Depois:
status = COMPLETED
```

O Trigger consegue perceber:

```sql
OLD.status  → PENDING
NEW.status  → COMPLETED
```

### Exemplo real

Sistema de pedidos:

```text
Pedido mudou de PENDING
        ↓
para COMPLETED
        ↓
Trigger registra essa alteração
```

Isso é muito útil para criar uma **tabela de histórico**.

---

## 14.9 DELETE

Executado quando uma linha é removida.

Exemplo:

```sql
AFTER DELETE
```

Nesse caso podemos acessar:

```sql
OLD.id
OLD.name
OLD.email
```

Como a linha está sendo excluída, não existe um `NEW` representando uma nova versão dela.

### Exemplo real

Um usuário é removido:

```text
DELETE user
    ↓
Trigger
    ↓
salva os dados antigos
    ↓
audit_log
```

Assim podemos manter um histórico da exclusão.

---

## 14.10 Combinações possíveis

Podemos combinar:

```text
BEFORE INSERT
AFTER INSERT

BEFORE UPDATE
AFTER UPDATE

BEFORE DELETE
AFTER DELETE
```

A escolha depende do momento em que queremos executar a lógica.

De forma simples:

```text
BEFORE → antes da operação

AFTER  → depois da operação
```

## 14.11 Exemplo completo

Imagine uma tabela de produtos:

```sql
CREATE TABLE products (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100),
    price DECIMAL(10,2)
);
```

Queremos registrar toda alteração de preço.

Criamos uma tabela de histórico:

```sql
CREATE TABLE price_history (
    id INT PRIMARY KEY AUTO_INCREMENT,
    product_id INT,
    old_price DECIMAL(10,2),
    new_price DECIMAL(10,2),
    changed_at DATETIME
);
```

Agora o Trigger:

```sql
CREATE TRIGGER after_product_price_update
AFTER UPDATE ON products
FOR EACH ROW
BEGIN
    IF OLD.price <> NEW.price THEN
        INSERT INTO price_history(
            product_id,
            old_price,
            new_price,
            changed_at
        )
        VALUES (
            NEW.id,
            OLD.price,
            NEW.price,
            NOW()
        );
    END IF;
END;
```

Quando alguém fizer:

```sql
UPDATE products
SET price = 120
WHERE id = 1;
```

O banco automaticamente poderá registrar:

```text
product_id | old_price | new_price
-----------|-----------|----------
1          | 100       | 120
```

A aplicação simplesmente executou o `UPDATE`.

## 14.12 Para que Triggers são usados?

Alguns usos comuns:

```text
Auditoria
    ↓
Registrar quem/o quê foi alterado

Histórico
    ↓
Guardar valores antigos

Validação
    ↓
Impedir determinados dados

Sincronização
    ↓
Atualizar informações relacionadas

Controle
    ↓
Executar alguma lógica automaticamente
```

### Exemplo em um sistema financeiro

Podemos ter:

```text
transactions
       ↓
   INSERT
       ↓
    Trigger
       ↓
transaction_audit
```

Assim, sempre que uma transação for criada, o banco registra automaticamente a operação.

## 14.13 Cuidado com Triggers

Triggers são poderosos, mas também podem deixar o sistema mais difícil de entender.

Por exemplo, a aplicação faz:

```sql
INSERT INTO transactions ...
```

Mas esse `INSERT` pode disparar:

```text
INSERT
  ↓
Trigger A
  ↓
UPDATE
  ↓
Trigger B
  ↓
INSERT
  ↓
Trigger C
```

Quem está olhando apenas o código da aplicação pode nem perceber que essas operações estão acontecendo.

Por isso, Triggers são melhores para **regras automáticas e bem definidas do banco**, principalmente coisas como auditoria e histórico.

Para regras de negócio complexas, muitas vezes é mais fácil manter a lógica na própria aplicação.
